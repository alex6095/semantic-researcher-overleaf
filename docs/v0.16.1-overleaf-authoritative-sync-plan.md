# v0.16.1 Overleaf-authoritative Local Replica plan

## Purpose

Overleaf is the canonical project state. A selected local folder is a durable,
editable working copy used by VS Code, Zed, shells, compilers, and agents. A
local change is not canonical until Overleaf accepts it. The synchronizer must
retain local intent while it obtains current remote state, submits an operation,
and observes the accepted remote result.

This is the durable task checklist. Update phase status and the work log in the
same commit as every material implementation or design decision.

## Non-negotiable invariants

1. An acknowledged Overleaf document or project-tree revision is the only
   canonical state.
2. The local tree remains normally editable. An agent or shell never needs to
   coordinate with VS Code before saving.
3. A dirty local editor buffer is never overwritten by remote input. A clean
   editor model may refresh from synchronized local disk state.
4. Event timing, mtime, and log order are diagnostic hints, never proof for
   conflict ordering or deletion.
5. Uncertain states preserve both copies and enter a durable conflict; they
   never select a winner silently.
6. `.output/**` and extension metadata are internal. A project PDF, PNG, ZIP,
   CSV, and other files remain syncable by default.

## Operation model

| Kind | Canonical server operation | Required precondition | Conflict policy |
| --- | --- | --- | --- |
| UTF-8 document update | join current doc, rebase, apply OT, observe ack | document id and current version | 3-way merge; overlap conflicts |
| File/media update | guarded upload/replace file entity | entity id and remote digest/revision | preserve both blobs |
| File creation | upload then add file entity | expected parent/tree state | same-name remote entity conflicts |
| Folder creation | add folder entity | expected parent/tree state | incompatible existing entity conflicts |
| Rename/move | entity-id tree operation | entity id, parent, tree state | remote move/rename conflicts |
| Delete | entity-id delete/tombstone operation | entity id/revision and clean local baseline | local divergence retains file |

## Durable state model

The manifest records last accepted remote state. Add a durable
pending-operation journal instead of treating a watcher event as an immediate
imperative request.

Every journal entry needs:

- operation id, kind, affected paths, and entity id when known;
- accepted remote identity/revision/digest and parent identity;
- stable local snapshot digest and recoverable snapshot/staging reference;
- creation time only for diagnostics, never ordering;
- lifecycle: `queued`, `reconciling`, `submitted`, `accepted`, or
  `conflict`.

Coalescing must retain the same user-visible outcome. A known rename must not
degrade into an unrelated delete plus create.

### Phase 1 - Local intent journal and status

- [ ] Persist stable local changes as operations before remote I/O begins.
- [ ] Coalesce repeated agent writes without losing final stable snapshot.
- [ ] Expose `Synced`, `Pending upload`, `Offline queued`,
      `Reconciling`, and `Needs attention` with counts.
- [ ] Keep offline work non-blocking; never show a modal merely because the
      connection is unavailable.
- [ ] Recover queued work safely after reload or Remote SSH reconnect.

### Phase 2 - Text documents

- [ ] Before each submission, obtain a coherent subscribed `joinDoc`
      revision and rebase local text against it.
- [ ] Submit an OT update with current base version and wait for matching
      applied operation/revision before accepting it in the manifest.
- [ ] Reconcile collaborator socket operations into clean local documents.
- [ ] Make version gaps, bad acks, and unjoinable docs fail closed into
      retry/conflict rather than stale pushes.

### Phase 3 - Files and project tree

- [ ] Model create, update, delete, rename, move, and mkdir as guarded entity
      operations.
- [ ] Upload source PNG/PDF/ZIP/CSV by default; exclude only configured
      generated output paths and .output.
- [ ] Verify remote entity identity and postconditions after every mutation.
- [ ] Preserve a binary conflict as two recoverable copies; never byte-merge.
- [ ] Block folder delete or rename containing unresolved descendant operations.

### Phase 4 - Inbound reconciliation and conflict UX

- [ ] Subscribe before trusting HTTP text snapshots; replay remote events in
      revision order.
- [ ] Apply remote changes directly only to clean local paths.
- [ ] Add Base/Local/Overleaf 3-way text diff with Accept Overleaf, Accept
      Local, and Apply Merged Result.
- [ ] Add Keep Local, Keep Overleaf, and Keep Both for binary/tree conflicts.
- [ ] Preserve resolution artifacts until Overleaf acknowledges the choice.

### Phase 5 - Acceptance matrix and release

- [ ] Closed and open text edits from VS Code, Zed, shell, and agent.
- [ ] PNG/PDF/ZIP create, replace, delete, rename, and folder move.
- [ ] Web edits while local is clean, dirty, offline, and reconnecting.
- [ ] Long local writer, atomic-save editor, and local compiler output.
- [ ] Remote delete versus prompt local recreation; subtree conflicts.
- [ ] Reload/restart journal recovery and account/project isolation.
- [ ] Full test suite, lint, production audits, package integrity, and signed-in
      Remote SSH / web validation.
